## Learning sequence and interaction contract
1. Why distributed computing: show a single-machine HashMap and a split/partial/merge diagram. Explain vertical/horizontal scaling and CPU/memory/I/O limits. Normalize the inconsistent scale in the handoff to 100 亿 = 10 billion, without attaching benchmark timings to it.
2. MapReducePipelineSimulator: five selectable steps plus Previous/Next/Reset. Partition 0 = e1–e4; partition 1 = e5–e8. Show raw rows, map pairs, local partial counts, routed records with source/target arrows, then final counts. A deterministic teaching partitioner routes equal joint keys to the same reduce partition; label it illustrative, not Spark's hash implementation. Highlight the two partial contributions to (A,10:01). Final counts must be 2,2,1,2,1 for A00,A01,B00,B01,C00. Use stable key colors and textual labels.
3. AggregationCostComparison: rows 1K/100K/1M, unique keys 10/100/1000, combine on/off. Model one input partition, all keys present and successfully combined: logical records rows vs min(rows,keys); show reduction ratio and bars. No claim about exact network bytes. Compare groupByKey+sum with reduceByKey, explain associative/commutative combining and weighted AVG via (sum,count): 130/3, not 57.5. Combiner is optional in Hadoop.
4. SparkArchitectureDiagram: selectable Driver, Cluster Manager, Worker, Executor, Partition and Task nodes. Cluster Manager allocates resources; Driver schedules tasks to Executor processes on workers. Show 100 partitions and slots 2/4/10/20 with ceil(100/slots) ideal waves, assuming one CPU per task and uniform task durations. Distinguish partitions, processes, machines and task attempts.
5. SparkDAGVisualizer: Read/Filter/Map/Local Aggregate in teaching Stage 0, shuffle boundary, Shuffle Read/Final Aggregate in Stage 1. Clicking a node explains the operation; clicking a stage shows its tasks and input partitions. Separate narrow one-to-one and wide many-to-many arrow views, with legends and labels. State that real boundaries come from the actual plan and partitioning.
6. API and physical plan: complete RDD, DataFrame and SQL examples for the same joint key. Clickable Scan → Partial HashAggregate → Exchange → Final HashAggregate → Result nodes show actual toy inputs/outputs. Include explain('formatted'), and explain this is a common illustrative plan, not a universal invariant. Provide scoped SQL/Python syntax highlighting without introducing a dependency or changing all existing code blocks.
7. SparkFailureSimulator: transformations initially planned; Run Action advances execution through dependencies. Simulate a failed task, retry, and lost shuffle output requiring relevant upstream recomputation. Reset restores initial state. Label simplified recovery, immutable/re-readable inputs and task-attempt identities. Separately illustrate successful +1000 write with lost acknowledgement and retry producing 2000 vs stable-key upsert preserving 1000. Explain sink transactions, idempotency and partition replacement; collect returns to Driver and is for small results.
8. ShuffleSkewSimulator: normal/hot distribution, salt counts 1/2/4/8, two-stage on/off. Display fixed physical reduce partition loads, max/mean skew ratio, baseline comparison and final aggregate. Deterministically distribute salt buckets over available partitions; eight salts must not silently become eight workers or guarantee collision-free scheduling. Salted partial results require final unsalting: show incomplete salted keys when second stage is disabled, restored counts when enabled. Model raw-equivalent work before effective map-side aggregation, not exact shuffle traffic or elapsed time. Explain COUNT with effective local combination can already shrink a hot key to a small number of partials; salting adds overhead and need not help. Preserve total input and final results across salts.
9. Application: diagram Click Tracking → Click DB, with Cron as a control trigger for Spark Batch (not a data store in the data path), aggregation → OLAP → Query Service → Dashboard. Estimate 10K/s × 300s = 3M and 100B/event ≈300MB decimal, excluding overhead. Explain when a single batch does not justify a cluster, freshness trade-offs, continuous Flink, Spark Structured Streaming, and historical/batch plus real-time roles. No Flink internals.

## Presentation and accessibility
Reuse quiet typography, borders and restrained semantic colors. Native buttons/radio controls support keyboard, focus, mobile wrapping, and programmatically exposed selected/expanded states. Stage transitions are user-driven; no autoplay required. Use reduced-motion support and polite concise status messages. SVG arrows have textual equivalents. Theory can use details/summary. Keep mobile diagrams readable with stacked cards or bounded internal scrolling, without page overflow. Figures support system dark preference; the surrounding existing site remains light-only as in the GROUP BY implementation.
