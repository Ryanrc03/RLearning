# Compute-bound vs Memory-bound

## 一句话

**compute-bound 的 kernel 卡在算不过来，memory-bound 的 kernel 卡在数据搬不过来；先判断是哪一种，才知道该往哪个方向优化。**

判断的依据是每从显存搬 1 个字节要做几次计算，这个比值叫算术强度。比值低就是 memory-bound，该想办法少搬数据；比值高就是 compute-bound，该想办法让计算单元跑满。

所以优化之前先**诊断**：资源加在不是瓶颈的那一边，完全没有效果。

## 先认单位：FLOP 与 GFLOP/s

**FLOP** 是一次浮点运算（floating-point operation）：一次加法或一次乘法各算 1 次。前面加单位前缀：G（giga）是 10⁹，T（tera）是 10¹²。**GFLOP/s** 是每秒做多少个 10⁹ 次浮点运算，衡量的是吞吐，也就是「算得多快」。

计算方法只有一行：

$$
\text{吞吐（GFLOP/s）} = \frac{\text{这个 kernel 总共做的浮点运算次数}}{\text{运行时间（秒）} \times 10^9}
$$

分子靠数，分母靠测。数的时候只看算法本身要做几次加和乘，不管硬件怎么实现：

| 任务 | 运算次数（FLOP） | 搬的字节（FP32，每个数 4 B） | 算术强度 FLOP / 字节 |
| --- | --- | --- | --- |
| 数组相加，N 个元素 | N（每个元素 1 次加法） | 12N（读 A、读 B、写 C） | 1/12 |
| N×N 矩阵乘 | 2N³（N² 个输出，每个 N 次乘 + N 次加） | 12N²（A、B、C 各搬一次） | N/6 |

**例 1：数组相加，1 亿个元素。** 运算次数是 10⁸ FLOP，要搬 1.2 × 10⁹ 字节。L40S 的带宽是 864 GB/s，光搬数据就要 1.2 × 10⁹ / 864 × 10⁹ ≈ 1.39 ms。吞吐 = 10⁸ / (1.39 × 10⁻³ × 10⁹) ≈ **72 GFLOP/s**，就是下面模拟器里那个数。

**例 2：矩阵乘，N = 1024。** 运算次数是 2 × 1024³ ≈ 2.15 × 10⁹，也就是 2.15 GFLOP，要搬 12 × 1024² ≈ 12.6 MB。按带宽算，搬数据要 12.6 MB / 864 GB/s ≈ 14.6 µs；按峰值算力 91.6 TFLOP/s 算，计算要 2.15 × 10⁹ / 91.6 × 10¹² ≈ 23.4 µs。计算比搬数据慢，所以这是 compute-bound，耗时 23.4 µs，吞吐 = 2.15 GFLOP / 23.4 µs ≈ **91.6 TFLOP/s**，正好顶到峰值。

两个例子合起来就是 roofline 的公式：吞吐 = min（峰值算力，算术强度 × 带宽）。拐点在 91.6 × 10¹² / 864 × 10⁹ ≈ 106 FLOP/字节。

几个容易混的地方：

- **FLOPs 和 FLOP/s 不是一回事。** FLOPs（小写 s）常指运算次数，比如「这个模型前向一次 4 GFLOPs」；FLOP/s 才是速度。GFLOPS 这种全大写写法两种意思都有人用，要看上下文。
- **一次 FMA（乘加 a·b + c）按 2 FLOP 算**，矩阵乘的 2N³ 就是这么来的。GPU 标称的峰值也是按 FMA 算 2 次得出的。
- **峰值要看精度。** 91.6 TFLOP/s 是 L40S 的 FP32 峰值；同一块卡用 Tensor Core 跑 FP16 / BF16，峰值高出好几倍。比较时分子分母要用同一种精度。
- **时间要测干净。** 用 CUDA event 只包住 kernel 本身，先跑几次预热，再取多次的平均；把主机和设备之间的拷贝算进去，吞吐会被严重低估。

## 一个模拟实验：数组相加 vs 矩阵乘

### 实验想做什么

在同一块 GPU（NVIDIA L40S）上放两类任务，看它们各自被什么卡住。

- **任务 1：数组相加**，`C[i] = A[i] + B[i]`，就是上一页的那个实验。
- **任务 2：矩阵乘**，两个 N×N 的矩阵相乘，深度学习里最常见的计算。
- **改变的变量**：矩阵大小 N，从 64 到 4096。

### 两边怎么做

<ArithmeticIntensityFigure />

数组相加的每个数只用一次就扔掉，所以搬 12 个字节只换来 1 次加法。矩阵乘里，A 的一行要和 B 的每一列都乘一遍，同一个数会被反复用 N 次，所以 N 越大，每个字节换来的计算越多。

### 你会观察到什么

在下面的模拟器里，从左往右依次点各个任务，应该能看到三件事：

1. **数组相加的点在斜线最左下。** 吞吐只有约 72 GFLOP/s，不到峰值算力的千分之一：计算单元几乎一直在等数据。
2. **矩阵乘的 N 越大，点沿着斜线往右上走。** N=64 和 N=256 仍然在斜线上，吞吐跟着 N 变大而上涨。
3. **N 到 1024 以后，点碰到平顶。** 它变成了 compute-bound，吞吐停在 91.6 TFLOP/s，N 再大也不会再涨。

<RooflineSimulator />

### 为什么会这样

- **斜线部分**，吞吐等于「每字节能算几次 × 带宽」。带宽是固定的，所以每字节算得越少，吞吐越低。数组相加的比值永远是 1/12，不管数组多长，它都只能待在左下角。这正是上一页 CPU 和 GPU 的差距最后停在带宽之比的原因。
- **平顶部分**，数据来得够快了，瓶颈变成计算单元本身。这时再加带宽没用，只能靠更强的算力（比如 Tensor Core）。
- **拐点约在 106 次/字节**，就是峰值算力除以带宽。任务的算术强度在拐点左边就是 memory-bound，在右边就是 compute-bound。

模拟器里的矩阵乘假设每个数只从显存搬一次。朴素的写法做不到这一点，同一个数会被反复从显存读出来，实际的点会往左移、掉回斜线上。怎样让每个数只搬一次，就是下一页 shared memory 和 tiling 要解决的问题。
