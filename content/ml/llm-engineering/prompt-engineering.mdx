# Prompt Engineering

## 一句话

**Prompt engineering 是在不改模型参数的前提下改写输入来改变答案：给它一个角色，放几个例子，让它先想再答，写清限制。**

模型是别人训好的、调不动的，产品里大部分「调模型」其实都在调这段文字。

## 为什么需要它

前面六章改的都是模型里面的东西：loss、优化器、正则、残差、[归一化](/notes/ml/dl-blocks/normalization/)。现在换一个处境：模型是别人训好的，参数拿不到，也没有预算重训，唯一能动的是送进去的那串 token。同一个任务，「把这条评论分一下类」和一段写清身份、例子、步骤和格式的 prompt，答案的稳定程度差得很远：前者今天回「负面」、明天回一段分析，后者每次都回「标签：中性。理由：……」。

## 怎么工作

<PromptEngineeringFigure />

四层各管一件事。**角色分配**（role assignment）告诉模型用谁的经验和口吻来答：质检员读「还行」和路人读「还行」给出的标签不一样。**少量例子**（few-shot）不解释规则，直接给三条「评论 → 标签 → 理由」，边界和格式一起被例子钉住；模型是顺着上下文里的模式往下写的，例子就是最强的模式。**先想再答**（chain-of-thought）让它先列出评论里的每个方面和各自的褒贬，再综合：没有这一步，它看到「贵」可能直接给负面；有了这一步，「价格贵了点」和「味道没变」会被分开权衡。**限制条件**（constraints）锁死标签集合、长度和格式，下游程序才能直接解析。

图里按阅读顺序拼：角色在最前，例子紧随其后，任务在中间，先想再答和限制贴在任务后面，因为靠近末尾的指令最不容易被忽略。右下的 token 数按「CJK 一字一个、英文一词一个」粗估：四层全开后是裸任务的七倍。这就是 prompt engineering 的全部代价，也是它的全部手段，模型的参数一个都没动。

## 代价与取舍

- 每一层都是 token：角色和限制几十个，例子上百个。每次请求都要重复付，延迟和费用跟着涨。
- 例子会被「照抄」：三条例子都是短评论，遇到三百字的长评论模型可能也只看前一句。例子要覆盖边界，不只覆盖典型。
- 先想再答让输出变长、变慢，而且「想」的那段也可能是编的；它改善的是稳定性，不保证正确性。
- 限制越死，模型越不会主动指出任务本身的问题（比如这条根本不是评论）。留一个「无法判断」的出口往往比三选一更安全。
- Prompt 只是模型看到的一部分：记忆、检索片段、工具结果会把它挤到一个角落，这是下一页。
