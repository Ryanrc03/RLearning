# Context Engineering

## 一句话

**Context engineering 是决定上下文窗口里放什么、放多少、按什么顺序放：prompt 只是其中一层，记忆、检索来的片段、工具结果和状态一起构成模型这一轮真正看到的东西。**

它是从「写一段好 prompt」到「搭一个能用的 LLM 应用」之间的那一步。

## 为什么需要它

上一页那段 337 个 token 的 prompt 写得再好，模型也不记得用户昨天说过什么，不知道这个商品的退货政策，更看不到订单系统里的数据。这些都得有人放进窗口。窗口是有限的，8k、32k 或 128k，每一段内容都在跟别的内容抢位置，多放一段就多花一段的钱和时间。没有这一层，要么该知道的没进来，模型只能编；要么什么都往里塞，窗口溢出，harness 只能从最早的消息截起，先丢的往往是记忆。

## 怎么工作

<ContextEngineeringFigure />

$$
\text{used} = \sum_{i} x_i\, t_i,\qquad x_i \in \{0, 1\},\qquad \text{used} \le B
$$

$t_i$ 是第 $i$ 段的 token 数，$x_i$ 是它这轮进不进窗口，$B$ 是窗口预算；实际还要给回答留出余量。图里的八段按在窗口里的先后排。**system** 是产品级的系统提示：身份、安全规则、输出格式，每轮都在。**拼好的 prompt** 就是上一页的四层，这里只占 337 个 token。**短期记忆摘要**：对话长了放不下原文，就把前 20 轮压成一段摘要。**长期记忆取回**：用户的历史偏好存在 vector DB 里，这轮只按相似度取回最相关的几条。**RAG 片段**：从商品文档里检索到的几段原文，模型照着它们答，而不是凭印象。**工具结果**：订单查询返回的 JSON 原文。**状态**：任务进行到哪一步、哪些变量已经填上。最后是**用户这轮**的消息。

默认状态下八段加起来 9,087 个 token，8k 的窗口已经溢出：条右端的斜纹是装不下的部分，表里累计数变红的行是从哪开始装不下。此时必须做选择：把 RAG 片段压到两段，把 JSON 换成一句摘要，或者干脆让这轮不查订单。切到 32k 全都装得下，但装得下不等于该装：每一段都在稀释别的段。

## 代价与取舍

- 记忆要压缩才放得下，压缩就会丢细节：摘要里没写的事，模型就当没发生过。什么该进摘要本身是个设计决定。
- 检索取回的不一定相关：vector DB 按相似度排，相似不等于有用，无关片段既占位置又误导。
- 工具结果的原文往往最胖，而模型只需要其中几个字段：先裁剪再放进去，比换更大的窗口便宜。
- 顺序有影响：模型对开头和结尾更敏感，中间的内容容易被忽略；要紧的指令放末尾，大段材料放中间。
- 窗口越大越容易偷懒把所有东西塞进去，费用和延迟线性涨，答案质量不一定涨。

## 再往下看

窗口里的内容决定了模型「知道什么」，但知道了也可能编。[Hallucination](/notes/ml/llm-engineering/hallucination/) 看采样那一步：下一个 token 是从一个概率分布里抽出来的，错的那些概率不是零，温度一高就被抽到。
