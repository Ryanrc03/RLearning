# 数据建模：先选对数据库，再设计表

系统设计里画完方框和箭头，下一步一定是“数据怎么存”。这一步分两层：选哪一类数据库，以及在选定的数据库里表怎么设计。

## 五类数据库

| 类型 | 代表 | 数据长什么样 | 擅长 |
| --- | --- | --- | --- |
| 关系型 | PostgreSQL、MySQL | 固定列的表，表之间用外键关联 | 关联查询、事务、强一致，大多数业务的默认选择 |
| 文档型 | MongoDB | 一条记录是一个 JSON 文档 | schema 灵活，字段说加就加，一次读出整个对象 |
| 键值 | Redis | 一个 key 对应一个值 | 极快，按 key 读写，做缓存、计数器、会话 |
| 宽列 | Cassandra、HBase | 按列族组织，每行可以有不同的列 | 海量写入、按时间顺序追加，比如传感器数据、日志 |
| 图 | Neo4j | 节点和边 | 关系本身就是重点的查询：好友的好友、推荐、风控 |

选型的直觉：先默认关系型，遇到它明显扛不住的地方再换。SQL 和 NoSQL 的具体对比，看[数据基础设施那一页](/notes/systems/data/overview/)。

## 设计 schema 时看三件事

- **数据量。** 一台数据库装得下吗？装得下就别分布式，复杂度不值得；装不下就要提前想好[分片键](/notes/systems/design/sharding/)。
- **访问模式。** 最频繁的几个查询是什么？schema 要为它们服务，索引也按它们建。先列查询，再设计表，而不是反过来。
- **一致性要求。** 有多严格？余额、库存必须强一致，放在支持事务的关系型数据库里；点赞数、浏览量差几秒没关系，可以异步更新、可以放缓存。

## 实体和键

把业务里的名词列出来就是实体：用户、帖子、评论、点赞。每个实体一张表，每张表要有：

- **主键（primary key）。** 唯一标识一行，通常是一个自增或随机生成的 id。
- **外键（foreign key）。** 表示关系：帖子表里有 user_id，指向用户表的 id，意思是“这条帖子是这个用户发的”。评论表有 post_id 和 user_id 两个外键；点赞表只需要 user_id 和 post_id，两个合起来就能唯一确定一次点赞。

## 面试里怎么用

系统设计题画完高层架构后，主动列出核心实体和它们的主键、外键，三五张表就够；然后说出最频繁的那个查询，以及为它建的索引；最后说数据库选型的理由，比如“订单要事务，用 PostgreSQL；浏览计数量大且能容忍延迟，放 Redis”。面试官要看的是你从访问模式推出设计，而不是背出所有数据库的名字。
