# 分片：一台数据库装不下的时候

数据量和写入量涨到一台机器扛不住，加内存、换更快的盘（纵向扩展）总有尽头。分片（sharding）是横向的办法：把一张大表按某个规则切成几块，每块放在一台机器上，每台只管自己那一部分。客户端的请求先到服务器，服务器算出这条数据在哪个分片，再去那台机器上读写。

分片要回答三个问题：按什么切，怎么分，切完之后哪些事变难了。

## 按什么切：分片键

分片键（shard key）决定一行数据去哪个分片，选错了后面全是麻烦。好的分片键有三个特点：

- **基数高。** 取值要足够多。按“国家”切，最多两百个值，中国一个分片就爆了；按用户 ID 切，几亿个值，怎么分都匀。
- **分布均匀。** 每个值对应的数据量差不多，不能有一个值特别大。
- **和查询对齐。** 最常见的查询最好只落在一个分片上。社交应用最常见的查询是“某个用户的所有帖子”，按 user_id 切，这个查询只问一台机器；按 post_id 切，就要问所有机器。

## 怎么分

- **按范围（range）。** id 0 到 1000 万在 S1，1000 万到 2000 万在 S2。范围查询方便，但新数据总是落在最后一个分片，新用户最活跃，最后一个分片又热又满。
- **按哈希（hash）。** shard = hash(key) % n。数据均匀散开，没有热点。但分片数一变，% 3 变成 % 4，几乎所有数据都要换地方，搬数据的那几个小时数据库压力巨大。
- **按目录（directory）。** 单独存一张查找表，记着每个 key 在哪个分片。最灵活，想怎么挪就怎么挪；代价是每次请求多查一次表，这张表本身还是单点，要做高可用。

**一致性哈希** 是为了解决哈希取模“加一台全部重排”而发明的：把分片和 key 都哈希到一个环上，key 归顺时针遇到的第一个分片。加一个分片，它只接走环上自己前面那一小段，其他 key 不动。再给每个分片放很多虚拟节点（virtual node），让每台机器在环上分散成许多小段，负载更均匀。

## 切完之后变难的三件事

**热点。** 分片键选得再好，也挡不住某一个 key 特别热：梅西发了一条帖子，一百万次互动全砸在他所在的分片上，其他分片每秒一千次。解法有两种：把热 key 再打散，比如用 hash(user_id + 帖子 id) 而不是只用 user_id，让同一个人的不同帖子落到不同分片；或者给这几个已知的超级大号一个专门的分片，在目录里单独路由。

**跨分片查询。** “全站点赞最多的 10 条帖子”要问每一个分片要它的前 10，汇总起来再排一次，分片越多越慢。解法：结果缓存起来，不要每次现算；或者反范式化，提前在写的时候多存一份冗余数据（比如单独维护一张全站热门榜），用存储换查询速度。

**跨分片一致性。** Alice 给 Bob 转 5 元，两人在不同分片上，扣款和加款必须一起成功或一起失败。一台数据库上的事务管不了两台机器，要换办法：

- **两阶段提交（2PC）。** 协调者先问所有分片“能不能做”，都说能才一起提交，有一个说不行就一起回滚。强一致，但过程中两边都锁着，慢；协调者中途挂了，大家一直锁着等，很脆弱。
- **Saga。** 把大事务拆成一串本地事务，每一步自己提交；某一步失败了，就按相反顺序执行前面每一步的补偿操作（退款、取消订单）。不锁、快，代价是中间有一段时间钱“暂时不见了”，而且每一步都要设计好怎么撤销。

## 面试里怎么用

被问到“数据量涨了 100 倍怎么办”：先说能不能只加只读副本或缓存解决（读多的话往往够了）；不够再分片，主动说出分片键选什么、为什么（基数、均匀、和主查询对齐），用一致性哈希方便以后扩容；最后点一句代价：跨分片的查询和事务会变难，转账这类用 Saga 补偿。
