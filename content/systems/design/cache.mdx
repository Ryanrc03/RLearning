# 缓存：把常用的东西放在近处

数据库查一次几毫秒，从内存里的缓存拿一次不到一毫秒。只要大部分请求都在读同一小撮数据，在数据库前面放一层缓存，就能把绝大多数读挡在数据库之外。最常见的缓存是 Redis，全称 Remote Dictionary Server：一台机器上的一个巨大的字典，所有应用服务器都能连上去。

这一页回答四个问题：缓存放在哪，读写怎么配合，满了踢谁，以及最常出的三种事故。

## 缓存放在哪

从离用户最远到最近：

- **外部缓存。** 一个独立的 Redis 集群，所有应用服务器共享。全局只有一份，一台应用服务器写进去，其他服务器都能读到。最常见。
- **进程内缓存。** 每个应用进程在自己内存里放一个小字典，连网络都不用过，最快。代价是每个进程各有一份，彼此不知道对方，同一个 key 在不同服务器上可能是不同的值。
- **CDN（内容分发网络）。** 把图片、视频、静态页面缓存到离用户最近的城市的服务器上。北京的用户从北京的节点拿，不用跨半个地球回源。
- **客户端缓存。** 浏览器或 app 自己存一份，连请求都不发。最快，但服务端最难控制它什么时候过期。

## 读写怎么配合

**遇到的问题。** 缓存和数据库存着同一份数据的两个副本。读的时候谁先？写的时候先改谁？改完另一边怎么办？

**四种模式。**

- **Cache-aside。** 应用自己管：读时先查缓存，miss 了自己查数据库再填回缓存；写时先写数据库，再删缓存。缓存挂了只是变慢，不会出错。最常用。
- **Read-through。** 读的逻辑一样，但“miss 了去数据库读”这件事由缓存层替应用做，应用只跟缓存说话。
- **Write-through。** 写缓存，缓存同步写数据库，两边都成功才返回。缓存永远是最新的，代价是写变慢，而且很多写进缓存的数据可能没人读。
- **Write-behind。** 写进缓存立刻返回，缓存稍后批量异步刷进数据库。写非常快；代价是缓存在刷盘前挂了，已经告诉用户“成功”的数据就丢了。只用于指标、计数这种丢一点也行的数据。

## 满了踢谁：淘汰策略

缓存的内存是有限的，满了必须踢掉一些。踢错了，下次又要回数据库。

- **LRU**，最久没用过的先踢。默认选择。
- **LFU**，用得最少的先踢。适合热度长期稳定的数据。
- **FIFO**，最早进来的先踢，不管热不热。最简单，效果通常最差。
- **TTL**，另一条独立的规则：每个 key 带过期时间，到点失效。它解决的是“数据会过时”，和“地方不够”是两回事，通常和上面某一种一起用。

## 三种常见事故

- **雪崩（stampede）。** 一个热 key 过期的那一刻，几千个请求同时 miss、同时去查数据库，把数据库打穿。解法：请求合并（single flight），同一个 key 同一时刻只放一个请求去数据库，其他人等这一个结果；或者在过期前后台提前刷新（cache warming）。
- **不一致。** 缓存和数据库是两份数据，总有窗口期不一样。写的时候删缓存（invalidate on write）是标准做法，但两个请求交错时仍可能把旧值写回缓存。兜底办法是给缓存设一个短 TTL，让错误最多活几十秒。对一致性要求极高的数据，关键操作直接读数据库。
- **热 key。** 一个明星发了动态，同一个 key 每秒被读几万次，而这个 key 只在一个缓存节点上，那个节点先被打满。解法：把热 key 复制几份分到不同节点；或者在应用本地再缓存一层，大部分读在本地就结束了。

## 面试里怎么用

画架构图时，在数据库前面加一个 Redis，然后主动说四句话：用 cache-aside，写数据库后删缓存；淘汰用 LRU 加 TTL；热点 key 过期用 single flight 防雪崩；对一致性敏感的数据不走缓存。面试官追问哪一句，就展开哪一句。
