# API：两个组件之间怎么说话

API 就是两个组件之间说话的约定：我能问你什么问题，用什么格式问，你会怎么回答。系统设计题画完架构之后，第二步通常是写出核心的几个 API，因为它把“系统要做什么”落到了具体的输入和输出上。

## 三种协议

- **REST。** 建立在 HTTP 之上，把一切看成资源，每个资源一个 URL，用 HTTP 动词操作：GET 读，POST 创建，PUT 整体更新，PATCH 部分更新，DELETE 删除。直观、通用、谁都能接，对外的公开接口默认用它。
- **GraphQL。** 客户端自己写出要哪些字段、嵌套到哪一层，服务端一次返回刚好这些。一个请求取齐一个页面要的所有东西，手机端特别喜欢。
- **RPC。** 把远程调用写得像调本地函数，比如 gRPC：在 .proto 文件里定义服务和消息，生成各种语言的代码，二进制传输最紧凑。服务之间的内部调用（比如索引服务、排序服务）用它。和 HTTP 的对比，看[网络那章的 HTTP vs gRPC](/notes/cs/networking/http-vs-grpc/)。

## 一个 REST 接口长什么样

**输入有三个地方可以放：**

- **路径（path）。** 标识资源本身：`GET /events/{id}`。
- **查询参数（query）。** 过滤、排序、分页：`GET /events?city=LA&date=2026-10-20`。
- **请求体（body）。** 创建或修改时的内容，通常是 JSON：`POST /events`，body 里写 title、location。

**响应用状态码说明结果：**

| 状态码 | 含义 |
| --- | --- |
| 200 | 成功 |
| 201 | 成功，并且创建了新资源 |
| 400 | 请求本身有问题，比如缺字段、格式不对 |
| 401 | 没登录，或者身份验证失败 |
| 404 | 要的资源不存在 |
| 500 | 服务端自己出错了 |

规律是：2 开头成功，4 开头是客户端的错，5 开头是服务端的错。客户端看到 4xx 不该重试，看到 5xx 可以带退避地重试。

## 分页

列表接口不能一次返回十万条，要分页。两种做法：

- **offset 分页。** “跳过前 20 条，给我 10 条”。简单，能直接跳到第几页。但翻得越深越慢，数据库要数过前面所有行；而且翻页时有新数据插进来，会看到重复或漏掉。
- **cursor 分页。** “给我比上一页最后一条更旧的 10 条”。不管前面插了多少新数据都不会重复，翻多深都一样快。信息流、聊天记录这种不断有新数据的列表都用它。代价是不能直接跳到第 37 页。

## 鉴权

API 要知道“是谁在调用”。两种主流做法：

| | Session token | JWT |
| --- | --- | --- |
| 登录后客户端拿到什么 | 一个随机字符串，像一张存包牌 | 一段签过名的 JSON，里面直接写着用户 ID 和过期时间 |
| 服务端怎么验证 | 拿这个字符串去 session 存储（比如 Redis）查对应的用户 | 用密钥验签名，不用查任何存储 |
| 好处 | 想让某人立刻下线，删掉服务端那条记录就行 | 无状态，任何一台服务器都能独立验证，适合很多服务 |
| 代价 | 每个请求多查一次存储 | 签发出去就收不回，只能等它过期，所以过期时间要短 |

## 面试里怎么用

架构图画完，写出三到五个核心 API，每个写清楚方法、路径、关键参数和返回。比如订票系统：`GET /events?city=&date=`，`GET /events/{id}`，`POST /bookings`（body 里是 event_id 和座位）。主动提一句列表用 cursor 分页、接口用 JWT 鉴权、POST 下单要带幂等键防止重复提交。
