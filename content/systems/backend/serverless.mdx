# Serverless

一句话：**你只写函数，不管服务器。** 代码交给云厂商，有请求来时它临时起一个实例跑你的函数，跑完就回收，按实际执行的次数和毫秒计费。没请求的时候没有任何机器在等你，也不花钱。名字有误导性：服务器当然还在，只是不归你管了。

## 它是什么

把“跑一个服务”这件事拆开，你会发现大部分工作和你的业务无关：买机器或开虚拟机、装操作系统和运行时、把进程跑起来、挂了重启、流量大了加机器、流量小了撤机器、给每台机器打补丁。Serverless 的承诺是这些全部由厂商做，你交付的东西缩小到一个函数：输入一个事件，输出一个结果。

事件可以是一个 HTTP 请求，也可以是“对象存储里新来了一个文件”“队列里多了一条消息”“到点了”。函数被事件触发，执行，返回。AWS 的 Lambda、Google 的 Cloud Functions、阿里云的函数计算都是这一类，统称 FaaS，函数即服务。

三种执行模型放在一起看：

| | 自己的机器 / 虚拟机 | 容器（Kubernetes） | Serverless |
| --- | --- | --- | --- |
| 你管什么 | 系统、运行时、进程、扩缩容 | 镜像和副本数，调度交给 K8s | 只有函数代码 |
| 没流量时 | 机器开着，照付 | 至少留一个副本 | 零实例，零费用 |
| 流量暴增时 | 手动加机器 | 按规则自动扩副本 | 自动起几千个实例 |
| 计费 | 按机器时长 | 按机器时长 | 按调用次数和毫秒 |
| 第一个请求 | 常驻，立刻 | 秒级 | 冷启动，几百毫秒到几秒 |

## 为什么存在

因为大多数服务的流量形状是**忽高忽低、大部分时间很闲**。用户上传一张图就生成一次缩略图，每晚跑一次报表，一个 webhook 一天被调几百次。为这种活开一台常驻机器，95% 的时间在空转，钱照付、补丁照打、半夜挂了照样要人起来重启。

Serverless 把这笔账反过来算：只为真正执行的那几百次付钱，闲着的时间厂商把机器给别人用。厂商之所以能这么做，是因为它把成千上万个客户的零碎流量叠在一起，叠出来的总负载是平稳的，一台机器可以轮流服务几十个客户的函数。你省的钱，就是这种复用省出来的。

## 怎么运作

跟着两个请求走一遍。关键是三个状态：没有实例、冷启动中、热实例。

<ServerlessLifecycle />

几个值得记住的点：

- **冷启动是真实的等待。** 实例从零起来要拉代码、起运行时、跑你的初始化。Python 和 Node 几百毫秒，Java 和 .NET 可能两三秒。请求连续时绝大多数是热的，请求稀疏时几乎每次都冷。
- **实例是无状态的。** 它随时可能被回收，内存里的东西留不住，连接池、缓存、计数器都不能指望它。状态要放外部的数据库、缓存或对象存储。
- **扩容就是多起实例。** 一千个请求同时来，厂商起一千个实例并行跑，你不用配任何规则。代价是下游的数据库可能被这一千个连接打垮，所以 serverless 后面通常要接连接池代理或队列。
- **执行时长有上限。** 通常几分钟到十几分钟，长任务要拆成多步，或者换别的跑法。

## 什么时候用

选执行模型的依据是**流量形状**，不是技术新旧。切换三种形状，看成本和尾延迟怎么变。

<ServerlessCostSim />

规律很稳定：偶发的活 serverless 便宜几个数量级；日夜波动的活容器扩缩最便宜、serverless 最省心但贵几倍，看你更在乎哪个；持续满载的活 serverless 反而最贵，因为按次计费没有批量折扣，而且你本来就不需要它的弹性。

## 代价

- **冷启动。** 对延迟敏感的接口是硬伤。缓解办法是付费预热一定数量的实例，但这又回到了“为空闲付钱”。
- **无状态。** 所有状态外置，多一次网络来回。
- **调试难。** 本地跑和线上不一样，日志要去厂商的控制台看，一条请求跨五个函数时要靠链路追踪拼起来。
- **厂商绑定。** 触发器、权限模型、部署方式都是厂商自己的，换云等于重写胶水层。
- **跑得多了反而贵。** 持续满负载按毫秒计费比包月机器贵好几倍。

## 面试里怎么用

放回 autonomy infra 的语境：训练、仿真、推理是持续的 GPU 密集负载，要常驻的、调度精细的集群，和 serverless 无关。Serverless 适合围绕它们的胶水：车辆日志上传完触发一个解析函数，训练任务结束触发一次评估，监控告警触发一条通知。

一个加分的说法是**按负载形状选执行模型**：持续的用常驻集群，偶发的用 serverless，中间的用容器加自动扩缩。这和选线程还是协程是同一个逻辑，看活里有多少“等”，等得多就别为等付钱。
