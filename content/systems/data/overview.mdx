# 数据基础设施：从一条日志到一个数据集

一辆车每天回传几百 GB 日志，一百辆车就是几十 TB。这些字节要经过五道关才能变成训练用的数据集：先决定来一条算一条还是攒一批再算，再决定消息放在日志里还是队列里，存下来时选表还是文档，落盘时选按行还是按列，最后决定先定结构再存还是先存了再说。每一道关都是一对选择，这页每节讲一对，正文下面配一个演示。

## 批还是流：Spark vs Flink

**遇到的问题。** 日志一条条进来，要算“每小时几次急刹”。什么时候算？

**两种世界观。** Spark 的世界观是批处理：数据已经落盘了，整体跑一遍。读全部、算全部、写结果，吞吐极高，逻辑简单，出错了整批重跑。Flink 的世界观是流处理：来一条算一条，按窗口输出，延迟秒级。

**代价在流这边。** 流处理要保存每个窗口算到一半的状态，机器挂了状态不能丢；一条事件不能算两次也不能漏；还有乱序：一条第 2 小时的事件第 5 小时才传上来，第 2 小时的窗口早关了，要用 watermark 决定等多久。所以能用批的地方不要硬上流。

典型分工：车辆日志回传后，流处理做实时监控和告警，批处理做大规模特征提取和数据集构建。

## 日志还是队列：Kafka vs 消息队列

**遇到的问题。** 日志从车上传到云端，中间要有个地方先接住，再分给几个不同的消费者。

**两种结构。** Kafka 把消息追加到一条带编号的日志里，不删，按时间保留几天到永久。每个消费者组自己记读到第几条，各自从头读，互不影响，晚来的能回放。传统消息队列（RabbitMQ 这一类）把消息排进队列，被哪个 worker 取走就删，没确认就自动投给别的 worker。

**用法完全不同。** Kafka 是“广播给所有想看的人，而且能回放”，训练数据、监控、回放三个组各读一遍同一份日志。队列是“把活分给工人，做完确认”，比如一万张图片要缩略图，十个 worker 分着做。

<KafkaVsMqDiagram />

和前面[网络那章](/notes/cs/networking/overview/)的 broker 对照：Kafka 就是那个“有 broker、先落盘”的实现，车内传感器流不用它，云端数据管道离不开它。

## 表还是文档：SQL vs NoSQL

**遇到的问题。** 日志解析出来的记录要存进数据库。车辆、工厂、行程之间有关联，字段还会随着新车型变化。

**两种结构。** 关系型数据库（PostgreSQL、MySQL）把数据拆成几张表，每张表固定的列，表之间靠 id 关联，一条 SQL 就能跨表查。文档型 NoSQL（MongoDB 这一类）每条记录是一个自包含的 JSON，相关的东西直接嵌在里面，没有固定结构。

**各自的代价。** 关系型改表结构是正式的事，要迁移；数据量涨到单机写不动时，跨机器的 join 和事务很难。NoSQL 加字段随手就加，按 id 分片天生容易，但没有 join，为了查得快常常重复存，工厂改名要改几十万条记录。

<SqlVsNosqlDiagram />

一句话选型：关联多、一致性要求高、规模可控，用关系型；写入量巨大、结构多变、查询模式固定，用 NoSQL。训练任务的元数据（哪个 checkpoint 最新、哪个数据集是哪个版本）属于前者。

## 按行还是按列：Parquet 和 Arrow

**遇到的问题。** 数据集最终是文件。同一张表，字节在磁盘上按什么顺序放？

**两种顺序。** 行存（CSV、JSON、数据库的行）把一条记录的所有字段挨在一起，取一条完整记录只要读一段连续字节，在线业务这样读。列存（Parquet）把一列的所有值挨在一起，算全车队的平均速度只读 speed 那一列，84 列的表不用白读 83 列；同一列类型相同、值相近，压缩率高 5 到 10 倍。训练和分析几乎都是“全部行、少数列”，所以数据集用 Parquet。

**再加一个词：Arrow。** Parquet 是列存在磁盘上的样子，Arrow 是列存在内存里的样子。Spark、Pandas、PyTorch 的 dataloader 都认 Arrow，数据在它们之间传递不用再序列化、反序列化。

标准答法：原始日志用行存写入，ETL 之后转成 Parquet 供训练读取，中间用 Arrow 避免拷贝。

## 先定结构还是先存了再说：数据仓库 vs 数据湖

**遇到的问题。** 一天 50 TB 原始日志，里面有点云、图片、CAN 信号、文本。分析师要查指标，训练要原始帧，都从这里来。

**两种做法。** 数据仓库（Snowflake、BigQuery、ClickHouse）要求写入之前先清洗、定好表结构，进去的都是整齐的表，分析师用 SQL 几秒出结果；代价是不规整的东西进不来，清洗是有损的，而且存储贵。数据湖把原始文件原样丢进对象存储，按日期和车辆分目录，几分钱一 GB，什么都能放；代价是没人定结构，每次查都要工程师写作业重新解释。

**现在的主流是湖仓一体。** 原始数据在湖里不动，常用指标用 Iceberg、Delta 这类表格式在湖上直接建成仓库的表，分析师查表，训练读原始文件，数据只存一份。

## 面试里怎么用

那道题：每天 100 辆车回传 50 TB 日志，怎么设计到可训练数据集的流程？沿着这页的五道关答：

1. 车端触发器筛选，只回传急刹、接管、置信度低的片段，不是全量。
2. 回传进 Kafka 做缓冲，解耦上传速率和处理速率，流处理做实时告警。
3. 原始文件落进对象存储的数据湖，按日期和车辆分区，不可变。
4. Spark 批作业解析、抽帧、提特征，输出 Parquet；场景元数据进数据库，支持“雨天夜间无保护左转”这种查询。
5. 选出的样本打版本号，生成 manifest，训练只认 manifest；常用指标在湖上建表给分析师。

要主动说的权衡：存储成本和召回率、处理延迟和吞吐、全量保留和采样保留。每一条都对应上面某一节的那对选择。
