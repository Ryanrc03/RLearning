# 从一根线到 Pub/Sub：网络是怎么一层层长出来的

计算机网络不是一次设计出来的。它是从两台机器一根线开始，每遇到一个解决不了的问题，就在外面加一层。每一层只依赖下一层的承诺，下一层的承诺不够用了，就换一个下一层。这页按这个顺序走六个阶段，每个阶段先说遇到了什么问题、加了什么、付出了什么代价，再用图走一遍。

## 一根线

**遇到的问题。** 两台机器用一根线连起来，A 往线上打 0 和 1，B 在另一头收。但连续的 0 和 1 不知道从哪开始、到哪结束，线上如果挂了第三台机器，也不知道这段数据是给谁的。

**加上什么。** 把数据切成一段段的帧（frame），每段前面加一个帧头：写上长度、校验码，还有收件人的网卡地址（MAC）。只有地址对上的那台机器才收下。这是最底下的一层。

**代价。** 一根线只能连几台。一百万台机器不可能两两拉线，中间必须有转发设备，而网卡地址是出厂烧死的随机数，没有规律，转发设备没法靠它判断往哪边走。

## IP：找到对方

**遇到的问题。** 需要一种有规律的地址，让中间的设备看一眼就知道往哪边转。

**加上什么。** 给每台机器一个 IP 地址，像邮政编码，前几位就能看出在哪个网。数据外面先套 IP 头（源地址、目标地址），再套帧头，这一包叫 packet。中间的转发设备叫路由器，它只看 IP 头，查自己的表决定下一跳，然后换一个新帧头发出去。IP 头一路不变，帧头每跳换一次，所以只要有路，任何两台机器都能通。

**代价。** IP 是尽力而为的：路由器忙了就丢，走不同路会乱序。它不通知、不重发、不排序。这是整个网络设计最重要的决定：底层保持简单，复杂的事往上推。另外 packet 到了机器，机器上开着十几个程序，IP 头没说该交给谁。

## 端口与 UDP

**遇到的问题。** 一台机器同时开着视频通话、游戏、下载，到达的 packet 该交给哪个程序。

**加上什么。** 在 IP 头里面再套一层，写两个端口号：源端口和目标端口。端口就是“这台机器上的第几个窗口”，每个程序占一个，接收方按目标端口分发。做这件事最薄的一层叫 UDP，头部只有 8 个字节。

**代价。** UDP 几乎就是“IP 加端口”，没有序号、没有确认，所以它继承了 IP 的全部不可靠。这不是缺陷，是刻意薄：视频通话、游戏位置、传感器帧正需要“丢了就丢，别为旧帧排队”。但文件和网页少一个字节就坏了。

## TCP：造出可靠

**遇到的问题。** 发一个文件，每个字节都得到、顺序不能错，但下面的 IP 会丢、会乱序。总不能让每个程序自己处理丢包。

**加上什么。** TCP 在 IP 上多做四件事：给每个字节编号；接收方回确认号，“N 之前的我全收到了”；发送方没等到确认就重传；接收方把乱序到达的先攒着，按序交付。传数据前先三次握手对上起始序号。另外还有拥塞控制：从慢开始发，丢包就减速，防止所有人一起把网络打垮。应用看到的是一条没有缺口的字节流，完全不知道底下丢过包。

**代价。** 握手多一个来回；丢一个包，后面已经到的也得攒着等它，叫队头阻塞；拥塞控制让速度忽快忽慢。所以 TCP 什么时候到说不准，UDP 要么很快到要么不到。两者在“丢一个包之后”的具体差别，看 [TCP vs UDP](/notes/cs/networking/tcp-vs-udp/)。

## HTTP 的三代

**遇到的问题。** TCP 给了一条可靠的字节流，但字节流里写什么、怎么表示“我要什么”“给你”，两边得约定。

**加上什么。** 应用层协议。HTTP 是浏览器和服务器之间的那一种：一段约定格式的文本，“GET /index.html，Host: example.com”，服务器回“200 OK”加正文。它不管丢包、不管路由，那些交给下面的层。

**它的演化全在怎么用底下的层。** HTTP/1.0 每个请求建一次 TCP 连接，握手一个来回。HTTP/1.1 把连接留着复用，但一条连接上同一时刻只能等一个回复，请求多了只能排队。HTTP/2 在一条 TCP 连接上开很多 stream 同时跑，头部压缩，却撞上 TCP 的队头阻塞：底下丢一个包，所有 stream 一起等。HTTP/3 干脆放弃 TCP，在 UDP 上自己做了一套叫 QUIC 的传输层，每个 stream 独立重传，握手和加密合成一个来回。

**这是整条线最好的例子。** HTTP 和 TCP、UDP 的关系不是“谁更高级”，是“谁坐在谁上面”。坐着的那层承诺不够用了，就换一层坐。

## 更上面：编码、调用、很多程序

**遇到的问题。** HTTP 规定了怎么说话，没规定说的内容怎么编码；HTTP 是给浏览器设计的，服务之间每秒几十万次小调用太重；前面都是两个程序的事，真实系统是几十个模块互相说话。

**加上什么。** 三样东西，各有深入对比的页面。

- **序列化。** JSON 是人能读的文本，每条都带字段名；Protobuf 是机器读的二进制，字段只带编号，小、快，字段改名不影响线上。看 [JSON vs Protobuf](/notes/cs/networking/json-vs-protobuf/)。
- **RPC。** 让调远程函数像调本地函数。gRPC 就是 HTTP/2 加 Protobuf。看 [HTTP vs gRPC](/notes/cs/networking/http-vs-grpc/)。
- **Pub/Sub 和 broker。** 发的人往一个 topic 喊一声，谁订阅谁听，发收双方互不认识；消息要不要先存到中间人那里，决定了能不能回放、延迟多低。看 [Request/Response vs Pub/Sub](/notes/cs/networking/reqresp-vs-pubsub/) 和 [Broker vs Brokerless](/notes/cs/networking/broker-vs-brokerless/)。

**连起来。** 一辆车的通信架构：车内传感器帧走 UDP 或共享内存，感知结果用 DDS 直连 Pub/Sub 分发；车到云，日志走 TCP 加 Protobuf；云端进 Kafka 可回放，服务之间用 gRPC。每一层都是为了解决下一层解决不了的那个问题而加的。

## 面试里怎么用

被问“车上为什么不用 HTTP”：HTTP 是一问一答，传感器数据是一个发很多收的流，而且 HTTP 坐在 TCP 上，旧帧重传没有意义。被问“为什么车上不用 Kafka”：broker 多一跳一落盘，车内要的是微秒级直达，错过的旧帧本来就不要。被问“HTTP/3 为什么换 UDP”：TCP 的队头阻塞让一个丢包拖住所有 stream，QUIC 在 UDP 上给每个 stream 单独重传。三个答案都是同一句话：每一层只依赖下一层的承诺，承诺不够用就换。
